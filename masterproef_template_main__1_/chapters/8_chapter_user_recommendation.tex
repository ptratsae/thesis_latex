\chapter{User-Side Job Recommender System}
\label{chap:user_recommendation}

This chapter describes the job recommender system built for users. The system learns dense representations of users $u \in \mathcal{U}$ and jobs $j \in \mathcal{J}$ and uses their similarity to rank job opportunities for each user $u$. This model is later used in Chapter~\ref{chap:congestion_balancing} as one of the two fundamental components for the congestion-aware two-phase job matching framework.

First, the dataset construction with negative sampling strategy is described in Section~\ref{sec:dataset_construction}. Then, the feature engineering is described in Section~\ref{sec:user_data_pipeline} followed by the architecture of the \gls{TT} model in Section~\ref{sec:user_arch}. Finally, the training procedure is described in Section~\ref{sec:user_training} and in Section~\ref{sec:user_inference} the usage of the trained model is discussed. The methods are applied in practice and the specific design choices and hyperparameters are reported in Section~\ref{sec:exp_user}.

\section{Dataset Construction with Negative Sampling}
\label{sec:dataset_construction}

Because the interaction log contains only positive examples (applications), negative examples are constructed during dataset creation. For each positive $(u,j)$ pair we sample a mixture of hard and easy negatives: a fraction of negatives are drawn from geographically close jobs while the remainder are sampled from distant jobs. This stratified negative sampling imitates the real-world scenario where most negative interactions are likely to be with jobs that are geographically distant, but a non-trivial portion of negatives will be with nearby jobs that the user has seen but chosen not to apply to. This approach prevents the model from learning trivial separations based only on coarse attributes and ensures it distinguishes true preference from mere co-location. The specific sampling ratio is reported in Section~\ref{sec:exp_user_datagen}.


\section{Feature Engineering}
\label{sec:user_data_pipeline}

The feature engineering process consists of two main stages: user feature 
processing and job feature processing. Both stages involve feature 
extraction, engineering and encoding to transform raw attributes 
into a vectorised format suitable for input into their respective 
towers. The design choices for each stage are described in the 
following sections.
\subsection{User Feature Processing}
\label{sec:user_features_processing}

User features are extracted from the user profile and engineered to form a comprehensive representation of each job seeker's profile.

\subsubsection{Feature Extraction and Engineering}

Raw user features such as demographics, education and location are 
merged with the user's employment history. Three domain-specific 
transformations are applied before encoding. First, the most recent 
job titles (up to three previous positions) are extracted and 
concatenated with recency labels to form a single career trajectory 
string:
\begin{equation}
\text{Recent\_JobTitle} = \text{``Current: } t_1 
\text{ | Previous: } t_2 \text{ | Earlier: } t_3\text{''}
\end{equation}
where $t_1, t_2, t_3$ are the three most recent job titles in reverse 
chronological order. Second, years since graduation is derived as 
$\text{current\_year} - \text{graduation\_year}$ and used as a proxy 
for professional experience, since elapsed time since graduation is a 
more informative signal than the raw date. Third, location fields are 
standardised by retaining city and state while dropping country and 
zip code, which are either redundant or near-zero variance at the 
scale of the dataset.

\subsubsection{Encoding}
\label{sec:user_embedding}

Each feature type is processed according to its nature:
\begin{itemize}
    \item \textbf{Numerical features (e.g. years of experience)} are standardised using z-score normalisation to ensure scale invariance at the \gls{MLP} input.
    \item \textbf{Categorical features with limited distinct values (e.g. state)} are label-encoded to integers and fed into learnable embedding layers rather than the \gls{MLP} directly, so no further normalisation is required. Categorical features that appear in both the user and job feature sets --- the location features --- are encoded using a shared vocabulary constructed jointly from both datasets, ensuring that the same value maps to the same integer index in both towers.
    \item \textbf{The job history} is embedded using a sentence transformer model (Qwen Embedding \cite{yang2025qwen3technicalreport}) to capture semantic information from the job titles. The resulting embedding is then truncated to $d_{\text{text}}$ dimensions to balance the contribution of the text signal with the other features. The choice of $d_{\text{text}}$ is discussed in Section~\ref{sec:exp_user_hyperparameters}.
\end{itemize}

\subsection{Job Feature Processing}
\label{sec:job_features_processing}

Job features undergo the same process as user features: numerical attributes are standardised using z-score normalisation, and categorical attributes are label-encoded to integers and passed through learnable embedding layers. The text feature (job title) is embedded using the same sentence transformer model and truncated to $d_{\text{text}}$ dimensions. \section{Two-Tower Model Architecture}
\label{sec:user_arch}

The \gls{TT} recommender consists of two separate neural networks. The user tower processes user features and the job tower processes job features. Both towers learn a dense vector representation of their respective input. The compatibility of a user–job pair $(u,j)$ is then measured as the dot product of these two vectors. 
This architecture is chosen because it handles the cold-start problem \cite{rama2019deeplearningaddresscandidate} effectively due to its generalisation capabilities \cite{berisha2023addressingcoldstartrecommendersystemsliteraturesurvey}. A user with no prior interaction history can still receive recommendations based on their profile features alone by using the learned user embedding. This property is essential given the temporal evaluation setup described in Section~\ref{sec:custom_split}. Additionally, it allows for efficient inference at scale, as both towers can be computed independently and the final similarity can be calculated with a simple dot product (see Section~\ref{sec:user_inference}).  

\subsection{User Tower}
\label{sec:user_tower}

The user tower is a multi-layer feedforward network that transforms the input user feature vector $\mathbf{x}_u$ with dimension $d_u$ into a $d$-dimensional embedding $\mathbf{e}_u$. All label-encoded categorical input features are first passed through learnable embedding layers (see Section~\ref{sec:prelim_embeddings}), producing dense representations for each categorical attribute. These are concatenated with the numerical features and text embedding to form the full input vector. This vector is then processed through a sequence of fully-connected layers with batch normalisation, ReLU activations and dropout regularisation.

The layer progression narrows from a wide hidden representation down to the final $d$-dimensional output, acting as a bottleneck that forces the network to learn a compressed and meaningful summary of the user profile. The architecture is detailed in Algorithm~\ref{alg:user_tower}.

\begin{algorithm}[H]
\caption{User Tower Forward Pass}
\label{alg:user_tower}
\begin{algorithmic}[1]
\Require Categorical features $\mathbf{c}_u$, numerical features $\mathbf{n}_u$ and text embedding $\mathbf{t}_u$
\For{each categorical feature $c_k$ in $\mathbf{c}_u$}
    \State $\mathbf{emb}_k \gets \text{Embedding}_{k}(c_k)$
\EndFor
\State $\mathbf{x}_u \gets [\mathbf{emb}_1, \ldots, \mathbf{emb}_K, \mathbf{n}_u, \mathbf{t}_u]$ 
\State $\mathbf{h}_1 \gets \text{Dropout}(\text{ReLU}(\text{BN}(\mathbf{W}_1^{(u)} \mathbf{x}_u + \mathbf{b}_1^{(u)})))$
\State $\mathbf{h}_2 \gets \text{Dropout}(\text{ReLU}(\text{BN}(\mathbf{W}_2^{(u)} \mathbf{h}_1 + \mathbf{b}_2^{(u)})))$
\State $\mathbf{e}_u \gets \mathbf{W}_3^{(u)} \mathbf{h}_2 + \mathbf{b}_3^{(u)}$
\Ensure User embedding $\mathbf{e}_u \in \mathbb{R}^d$
\end{algorithmic}
\end{algorithm}

\subsection{Job Tower}
\label{sec:job_tower}

The job tower mirrors the user tower architecture exactly, processing job features $\mathbf{x}_j$ (dimension $d_j$) to produce a $d$-dimensional job embedding $\mathbf{e}_j$. The same pattern of categorical embeddings concatenated with numerical features and text embedding, followed by the bottleneck \gls{MLP}, is applied. The only structural difference is the input dimension, which depends on the number of job-specific features. This symmetry is intentional: it ensures that user and job embeddings live in the same $d$-dimensional space, making the dot product a meaningful similarity measure. The architecture is detailed in Algorithm~\ref{alg:job_tower}.
\begin{algorithm}[H]
\caption{Job Tower Forward Pass}
\label{alg:job_tower}
\begin{algorithmic}[1]
\Require Categorical features $\mathbf{c}_j$, numerical features $\mathbf{n}_j$, and text embedding $\mathbf{t}_j$
\For{each categorical feature $c_k$ in $\mathbf{c}_j$}
    \State $\mathbf{emb}_k \gets \text{Embedding}_{k}(c_k)$
\EndFor
\State $\mathbf{x}_j \gets [\mathbf{emb}_1, \ldots, \mathbf{emb}_K, \mathbf{n}_j, \mathbf{t}_j]$ 
\State $\mathbf{h}_1 \gets \text{Dropout}(\text{ReLU}(\text{BN}(\mathbf{W}_1^{(j)} \mathbf{x}_j + \mathbf{b}_1^{(j)})))$
\State $\mathbf{h}_2 \gets \text{Dropout}(\text{ReLU}(\text{BN}(\mathbf{W}_2^{(j)} \mathbf{h}_1 + \mathbf{b}_2^{(j)})))$
\State $\mathbf{e}_j \gets \mathbf{W}_3^{(j)} \mathbf{h}_2 + \mathbf{b}_3^{(j)}$
\Ensure Job embedding $\mathbf{e}_j \in \mathbb{R}^d$
\end{algorithmic}
\end{algorithm}

\subsection{Prediction Layer}
\label{sec:user_prediction}

The final user-job compatibility score is computed as the dot product of the two learned embeddings:
\begin{equation}
s(\mathbf{e}_u, \mathbf{e}_j) = \mathbf{e}_u \cdot \mathbf{e}_j = \sum_{i=1}^{d} (\mathbf{e}_u)_i \cdot (\mathbf{e}_j)_i
\end{equation}

Higher scores indicate stronger predicted similarity between a 
user's preferences and a job's characteristics. At inference time, 
the raw score is used directly for ranking, as discussed in 
Section~\ref{sec:user_inference}.

\section{Training Procedure}
\label{sec:user_training}

The model is optimised using binary cross-entropy computed on 
sigmoid-scaled dot-product scores. Concretely, the raw compatibility 
score $\hat{y}_i = s(\mathbf{e}_u, \mathbf{e}_j)$ is mapped to the $[0,1]$ interval via the sigmoid function $\sigma$, and the binary 
cross-entropy is computed as:
\begin{equation}
\mathcal{L} = -\frac{1}{N} \sum_{i=1}^{N} \left[ y_i 
\log\big(\sigma(\hat{y}_i)\big) + (1 - y_i) 
\log\big(1 - \sigma(\hat{y}_i)\big) \right].
\end{equation}
Here $y_i \in \{0,1\}$ is the ground-truth label.

The model is optimised using the Adam optimiser. Early stopping 
based on validation loss is applied to prevent overfitting, halting 
training when validation loss does not improve for a fixed number 
of epochs.

Specific hyperparameter values are reported in 
Section~\ref{sec:exp_user_hyperparameters}. Design choices such 
as whether to apply L2 normalisation are determined through an 
ablation study in Section~\ref{sec:exp_user_ablation}, and the 
final model results are reported in 
Section~\ref{sec:user_results}.
\label{sec:user_inference}
At inference time, recommendations are generated efficiently by precomputing the output of the job tower for each $j \in \mathcal{J}$ and caching them in memory. For each user $u$, only the user tower forward pass is executed, followed by a single matrix multiplication against the precomputed job matrix for all $j \in \mathcal{J}$. This reduces per-user recommendation time to one matrix multiply regardless of $|\mathcal{J}|$.
 
Either raw scores or sigmoid probabilities could be used for ranking. The raw dot product scores are used directly for ranking in Section~\ref{sec:exp_user_inference}. However, the hybrid model described in Chapter~\ref{chap:congestion_balancing} uses the sigmoid probabilities for ranking because the recruiter model produces probability estimates, so using the same scale for both components simplifies the aggregation step. 
 
In Section~\ref{sec:exp_user_inference} examples of the generated recommendations are provided, along with a qualitative discussion of the relevance of the jobs, the geographic coherence and the difference between a user with a rich job history and a user with no job history. The scores produced at inference time feed directly into the congestion balancing framework described in Chapter~\ref{chap:congestion_balancing}.
