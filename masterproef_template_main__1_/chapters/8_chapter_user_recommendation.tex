\chapter{User-Side Job Recommendation System}
\label{chap:user_recommendation}

This chapter details the job recommendation system built for users using PyTorch, consisting of the preprocessing of the data and the architecture of the two-tower model. This model will be used in Chapter \ref{chap:congestion_balancing} to implement the user-side congestion reduction strategy. The need for a two-tower \gls{RS} is due to the fact that a neural network can deal with the cold start problem \cite{rama2019deeplearningaddresscandidate}, which is important considering how the dataset is split (see Section \ref{sec:custom_split}). 

First, in Section \ref{sec:user_arch}, the architecture of the two-tower model is explained. Then, in Section \ref{sec:user_data_pipeline}, the data pipeline and feature engineering techniques are described. In Section \ref{sec:user_training}, the training procedure and optimization are discussed. For experiments and results related to the user-side recommendation system, please refer to Chapter \ref{chap:experiments}.

\section{Architecture: The Two-Tower Model}
\label{sec:user_arch}
The two-tower model is trained and evaluated on the CareerBuilder Job Recommendation dataset (see Chapter \ref{chap:dataset_overview} for a comprehensive dataset overview). The model consists of two separate neural networks: one for processing the user features, the user tower, and one for processing the job features, the job tower. Each tower learns a vector representation of its respective features. The output of both towers is then combined to produce a final matching score for a user-job pair. The architecture is designed to capture complex interactions between user and job features.

\subsection{User Tower}
\label{sec:user_tower}
The user tower consists of a multi-layer feedforward neural network that transforms the input user features into a dense embedding vector. This embedding captures the underlying preferences and characteristics of the user, which can then be used to compute similarity with job embeddings from the job tower.

\subsubsection{Input Layer}
\begin{listing}[H]
\begin{minted}{python3}
self.user_embeddings = nn.ModuleList([
    nn.Embedding(card, 16) for card in num_user_cat
])
\end{minted}
\caption{User embedding layer initialization in the two-tower model}
\label{lst:user_embeddings}
\end{listing}

Categorical features are converted to 16-dimensional embeddings using learnable embedding layers. These embeddings are then concatenated with numeric features (e.g., years of experience, work history count). The total input dimension is calculated as:

\begin{listing}[H]
\begin{minted}{python3}
user_input_dim = len(num_user_cat) * 16 + num_user_numeric
\end{minted}
\caption{User input dimension calculation}
\label{lst:user_input_dim}
\end{listing}

\subsubsection{Neural Network Stack}

The user tower consists of three fully-connected layers with regularization:
\begin{itemize}
    \item \textbf{Layer 1}: Linear(user\_input\_dim $\rightarrow$ 512) with batch normalization, ReLU, and 30\% dropout.
    \item \textbf{Layer 2}: Linear(512 $\rightarrow$ 256) with batch normalization, ReLU, and 20\% dropout.
    \item \textbf{Output Layer}: Linear(256 $\rightarrow$ 64) producing a 64-dimensional user embedding.
\end{itemize}

The decreasing layer sizes (512 $\rightarrow$ 256 $\rightarrow$ 64) act as a bottleneck, forcing the network to learn a compressed and meaningful representations of user profiles. The implementation of this tower is shown here:

\begin{listing}[H]
\begin{minted}{python3}
self.user_tower = nn.Sequential(
    nn.Linear(user_input_dim, 512),
    nn.BatchNorm1d(512),
    nn.ReLU(),
    nn.Dropout(0.3),
    nn.Linear(512, 256),
    nn.BatchNorm1d(256),
    nn.ReLU(),
    nn.Dropout(0.2),
    nn.Linear(256, output_dim)
)
\end{minted}
\caption{User tower architecture in the two-tower model}
\label{lst:user_tower}
\end{listing}

\subsection{Job Tower}
\label{sec:job_tower}

The job tower mirrors the architecture of the user tower to process job-related features, learning compact representations for each job. The only difference is the input dimension, which depends on the number of job features.

\subsubsection{Input Layer}

\begin{listing}[H]
\begin{minted}{python3}
self.job_embeddings = nn.ModuleList([
    nn.Embedding(card, 16) for card in num_job_cat
])
\end{minted}
\caption{Job embedding layer initialization in the two-tower model}
\label{lst:job_embeddings}
\end{listing}

Similar to the user tower, categorical job attributes (e.g., city, state) are embedded to 16 dimensions. Numeric features, including the Qwen3 text embeddings of job titles, are concatenated with these categorical embeddings. The total input dimension mirrors the user tower calculation:

\begin{listing}[H]
\begin{minted}{python3}
job_input_dim = len(num_job_cat) * 16 + num_job_numeric
\end{minted}
\caption{Job input dimension calculation}
\label{lst:job_input_dim}
\end{listing}

\subsubsection{Neural Network Stack}

The job tower employs an identical layer progression as the user tower:
\begin{itemize}
    \item \textbf{Layer 1}: Linear(job\_input\_dim $\rightarrow$ 512) with batch normalization, ReLU, and 30\% dropout.
    \item \textbf{Layer 2}: Linear(512 $\rightarrow$ 256) with batch normalization, ReLU, and 20\% dropout.
    \item \textbf{Output Layer}: Linear(256 $\rightarrow$ 64) producing a 64-dimensional job embedding.
\end{itemize}

The implementation of the job tower is as follows:

\begin{listing}[H]
\begin{minted}{python3}
self.job_tower = nn.Sequential(
    nn.Linear(job_input_dim, 512),
    nn.BatchNorm1d(512),
    nn.ReLU(),
    nn.Dropout(0.3),
    nn.Linear(512, 256),
    nn.BatchNorm1d(256),
    nn.ReLU(),
    nn.Dropout(0.2),
    nn.Linear(256, output_dim)
)
\end{minted}
\caption{Job tower architecture in the two-tower model}
\label{lst:job_tower}
\end{listing}

\subsection{Prediction Layer}
\label{sec:user_prediction}

The final user-job matching score is computed via the dot product of the learned user and job embeddings:
\begin{equation}
\text{score} = \text{user\_vec} \cdot \text{job\_vec} = \sum_{i=1}^{64} \text{user\_vec}_i \times \text{job\_vec}_i
\end{equation}

This dot product measures the similarity between the learned user and job representations. Higher scores indicate better matches, while lower scores suggest poor alignment between user preferences and job characteristics. This approach allows the model to capture non-linear relationships between user and job features through the multi-layer architecture. The complete two-tower model implementation in PyTorch is provided in Appendix \ref{app:two_tower_model}.

Note that L2 normalization of the output vectors was considered. Extra information about this design choice and its impact on performance is provided in Chapter \ref{chap:ablation}.

\section{Data Pipeline and Feature Engineering}
\label{sec:user_data_pipeline}

The raw data needs to be preprocessed before it can be used by the two-tower model. The data pipeline consists of 3 main stages: user feature processing (\ref{sec:user_features_processing}), job feature processing (\ref{sec:job_features_processing}), and text embedding generation (\ref{sec:text_embedding}) which is applied to the user and job features. Each stage is designed to handle large-scale data efficiently due to the size of the CareerBuilder dataset. The training data generation is explained in Chapter \ref{chap:experiments}.


\subsection{User Feature Processing}
\label{sec:user_features_processing}

User features are extracted and engineered to create a comprehensive representation of each job seeker's profile.

\subsubsection{Feature Extraction and Merging}

Raw user features (demographics, education, location) are merged with user employment history. The most recent job titles (up to 3 previous positions) are extracted and concatenated with recency labels:
\begin{equation}
\text{Recent\_JobTitle} = \text{``Current: JobTitle}_{1}\text{ | Previous: JobTitle}_{2}\text{ | Earlier: JobTitle}_{3}\text{''}
\end{equation}

This concatenation is embedded using the Qwen3-Embedding-0.6B model to capture the semantic meaning of the user's career trajectory (see Section \ref{sec:user_embedding}).

\subsubsection{Feature Engineering}

Several domain-specific features are engineered from raw attributes:

\begin{itemize}
    \item \textbf{Years Since Graduation}: Calculated from the graduation date as $\text{current\_year} - \text{graduation\_year}$. Missing values are imputed with the median. This is done because the graduation date itself is not as informative as how long ago the user graduated, which can indicate career stage.
    \item \textbf{Location Standardization}: Country and ZipCode columns are dropped. Country is dropped because the dataset is US-based. ZipCode is dropped as it is redundant given City and State, and introduces noise due to missing or inconsistent values. City and State are retained.
\end{itemize}

\subsubsection{Embedding and Encoding}
\label{sec:user_embedding}

The engineered features are processed based on their data type:

\begin{itemize}
    \item \textbf{Recent Job History}: The Recent\_JobTitle field is encoded into a dense 100-dimensional vector using the Qwen3 Embedding Model (0.6B), capturing semantic meaning of job titles and career progression. This embedding is stored as 100 columns prefixed with \texttt{ft\_recent\_job0} through \texttt{ft\_recent\_job99}. The choice of 100 dimensions is to not allow the text embedding to completely dominate the input signal.
    \item \textbf{Numeric Features}: Features such as years of experience are standardized using z-score normalization (StandardScaler) to have mean 0 and standard deviation 1, ensuring scale invariance across the \gls{MLP} input.
    \item \textbf{Categorical Features}: Features such as education level and other discrete attributes are label-encoded independently per feature file, mapping each unique value to an integer starting from 1 (0 is reserved for missing values). The only exception is City and State, which are encoded using a shared vocabulary across both user and job feature files (see Section \ref{sec:location_encoding}), ensuring that the same location maps to the same embedding index in both towers. All label-encoded features are fed into learnable embedding layers, not the \gls{MLP} 
    directly, so normalization is not required.
\end{itemize}

\subsection{Job Feature Processing}
\label{sec:job_features_processing}

Job features are processed in a scalable manner using chunked processing to handle large job datasets efficiently.

\subsubsection{Data Organization}

Raw job data is separated into three categories:
\begin{itemize}
    \item \textbf{Meta Columns}: JobID, WindowID, StartDate, EndDate (preserved without transformation)
    \item \textbf{Text Columns}: Title, Description, Requirements (extracted for separate text cleaning and embedding)
    \item \textbf{Feature Columns}: All numerical and categorical attributes used for the two-tower model
\end{itemize}

\subsubsection{Chunked Processing Strategy}

Given the large size of the job dataset, processing is performed in chunks of 50,000 records using a two-pass approach:

\begin{enumerate}
    \item \textbf{First Pass}: Iterate through all chunks to collect unique categorical values and compute scaling statistics (mean, variance) from numerical features across the entire dataset.
    \item \textbf{Second Pass}: Apply learned encoders and scalers consistently to transform the data, ensuring that categorical mappings and numerical scaling are coherent across all jobs.
\end{enumerate}

\subsubsection{Feature Transformation}

During the second pass, features are transformed as follows:

\begin{itemize}
    \item \textbf{Numerical Features}: Standardized using StandardScaler fitted on the full dataset, ensuring consistent scaling across all chunks.
    \item \textbf{Categorical Features}: Mapped to integers using a consistent encoding dictionary built from all unique values (1-indexed; 0 for missing values).
    \item \textbf{Location Features}: City and State are retained and label-encoded. As they are categorical features which are present in both user and job datasets, a shared encoding dictionary is created to ensure that the same city/state maps to the same integer in both towers (see Section \ref{sec:location_encoding}).
\end{itemize}

\subsection{Text Cleaning and Embedding}
\label{sec:text_embedding}
Text data from job postings is processed to extract semantic information through cleaning and embedding.

\subsubsection{Text Cleaning}
Job titles and descriptions often contain HTML tags, special characters, and inconsistent formatting. The cleaning process:
\begin{enumerate}
    \item Removes HTML tags using the BeautifulSoup parser.
    \item Converts text to lowercase for consistency.
    \item Strips leading and trailing whitespace.
\end{enumerate}

\subsubsection{Semantic Embedding with Qwen}
The cleaned job titles are encoded into dense vectors using the Qwen3 Embedding Model (0.6B). The embedding process:
\begin{enumerate}
    \item Encodes each job title into a 100-dimensional vector, truncated from the full embedding dimension. The truncation serves two purposes: computational efficiency, and preventing the text embeddings from dominating the input signal. 
    With 100 Qwen dimensions out of a total job tower input of $2 \times 16 + 100 = 132$ dimensions, the text embedding represents a significant, as this contains the most information, but not overwhelming portion of the input, allowing categorical and other numerical features to contribute meaningfully to the learned job representation. The same 100-dimensional truncation is applied to user job history embeddings for consistency.
    \item Normalizes embeddings to unit norm to ensure comparable similarity scores across the corpus.
    \item Stores embeddings with columns prefixed as \texttt{qwen\_0} through \texttt{qwen\_99}.
\end{enumerate}

These Qwen embeddings capture semantic relationships between job titles (e.g., ``Software Engineer'' and ``Developer'' have similar embeddings), enabling the job tower to learn meaningful job-to-job relationships beyond categorical attributes.

\subsubsection{Merging with Job Features}
Qwen embeddings are merged with the processed job features using JobID as the key. Missing embeddings (if any) are filled with 0. The final job feature matrix contains:
\begin{equation}
\text{job\_features} = [\text{meta\_cols},\ \text{numerical\_features},\ \text{categorical\_features},\ \text{qwen\_embeddings}]
\end{equation}

\subsection{Cross-Tower Location Consistency}
\label{sec:location_encoding}

An important preprocessing step that emerged from empirical investigation is ensuring that the same location (city/state) is mapped to the same integer in both the user and job feature files. Without this step, user features and job features are label-encoded independently, meaning city ``New York'' might be encoded as 42 in the user file and 137 in the job file. As a result, user city embedding 42 and job city embedding 42 would refer to completely different cities, and the model would learn no meaningful location signal from the embedding layers.

To fix this, a shared vocabulary is constructed after both feature files are generated:
\begin{enumerate}
    \item All unique city and state values from both user and job datasets are collected.
    \item A single shared mapping is created from location string to integer.
    \item Both user and job feature files are re-encoded using this shared vocabulary.
\end{enumerate}

The impact of this step is validated in the ablation study (Section \ref{sec:ablation}), where including location features with the shared vocabulary significantly outperforms excluding them.

\section{Training and Evaluation}
\label{sec:user_training}

\subsection{Training Configuration}
\label{sec:training_config}

The model is trained on the Train split (Windows 1--4) using the Adam optimizer with a learning rate of 0.001 and a batch size of 1024. The output embedding dimension is set to 64 for both towers. Early stopping is applied with a patience of 5 epochs based on validation loss, preventing overfitting. In the final training run, the model converged at epoch 11 out of a maximum of 50 epochs, confirming that early stopping is effective for this dataset.

\subsection{Loss Function and Optimization}
\label{sec:loss_function}

The model is optimized using Binary Cross-Entropy with Logits loss (\texttt{BCEWithLogitsLoss}), which combines a sigmoid activation with the binary cross-entropy loss in a numerically stable way:
\begin{equation}
\mathcal{L} = -\frac{1}{N} \sum_{i=1}^{N} \left[ y_i \log(\sigma(\hat{y}_i)) + (1 - y_i) \log(1 - \sigma(\hat{y}_i)) \right]
\end{equation}

where $y_i \in \{0, 1\}$ is the ground truth label and $\hat{y}_i$ is the raw dot product score output by the model. The sigmoid $\sigma$ maps the unbounded dot product to a probability. 

At inference, the raw dot product scores are used for ranking. This is because the sigmoid funtion transforms scores to a [0, 1] range, where high-confidence matches map to 1.0000 in float32 precision while raw dot product scores are still distinguishable. 
\subsection{Performance Evaluation Metrics}
\label{sec:user_eval_metrics}

Model performance during training is assessed using the following metrics computed on the validation set:
\begin{itemize}
    \item \textbf{AUC-ROC}: \gls{ROC-AUC}, measuring the model's ability to rank positive samples higher than negatives across all score thresholds. This is used as the primary early stopping criterion.
    \item \textbf{Accuracy}: Percentage of correctly classified user-job pairs at a 0.5 probability threshold.
    \item \textbf{Hit@K}: Whether at least one relevant job appears in the top-K recommendations for a user.
    \item \textbf{Recall@K}: Fraction of a user's relevant jobs that appear in the top-K recommendations.
    \item \textbf{NDCG@K}: \gls{NDCG}, measuring ranking quality by penalizing relevant items ranked lower.
\end{itemize}

It is important to note that Hit@K, Recall@K, and NDCG@K computed during validation are measured over a small per-user candidate pool (the balanced validation set), not against all jobs. These metrics are therefore optimistic relative to real-world inference, where a user is ranked against the full job pool. \gls{ROC-AUC} is the most reliable metric during training as it is less sensitive to candidate pool size.


\subsection{Inference and Post-Processing}
\label{sec:inference_postprocessing}

At inference time, recommendations are generated efficiently using a precomputed job vector cache. All job embeddings from the job tower are computed once and stored in GPU memory. For each user, only the user tower forward pass is executed, followed by a batched dot product against all precomputed job vectors. This reduces per-user recommendation time to a single matrix multiplication.

Since the model is trained without location features as a discriminative signal (by design of the city-based negative sampling), geographic preference is applied as a post-processing step. Jobs located in the same state as the user are boosted in ranking, ensuring geographically relevant recommendations without conflating location preference with semantic job-fit during training. This separation of concerns — semantic relevance learned by the model, geographic preference applied post-hoc — allows each component to be tuned and evaluated independently.

At inference, recommendations are restricted to jobs from the current test window (Window 7) to avoid recommending jobs from earlier windows that may no longer be active.
