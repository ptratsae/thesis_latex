\section{Experiment Settings}
\label{sec:exp_settings}

\subsection{Dataset}
\label{sec:exp_dataset}
All experiments are conducted on the CareerBuilder Job Recommendation dataset~\cite{careerbuilderdataset}, consisting of real-world job applications, user profiles and job postings from CareerBuilder.com over a 13-week period. The dataset is organised into seven consecutive 13-day temporal windows where users apply to jobs which are active in the same window. Table~\ref{tab:dataset_stats} summarises the scale of the full dataset.

Rather than using the original within-window train/test labels provided by the dataset, a temporal split across windows is applied (Figure~\ref{fig:custom_temporal_split}). Windows 1--4 form the training set and Windows 5--7 form the validation and test set, with Windows 5--6 used for validation and Window 7 reserved for final evaluation.

Users marked \texttt{Split=Test} are excluded entirely (22,838 users). These users made five or more applications during the withheld 4-day test period of the original competition. Of these, 43\% have no recorded interactions in the training period whatsoever, as their only observable activity falls within the withheld test period. Including them would introduce users with structurally missing interaction records into the evaluation set, so they are excluded entirely.

This design has three consequences. First, there is a strict temporal boundary: the model never sees any interaction from the evaluation period during training. Second, the evaluation is a genuine cold-start scenario — no user appears in both the training and evaluation sets. Third, using all active users from each window group (rather than filtering by activity thresholds) avoids biasing the evaluation towards highly-engaged users. Table~\ref{tab:split_stats} shows the resulting split sizes.

\subsection{Hardware and Software Configuration}
\label{sec:hardware}

All experiments are run on the Artificial Intelligence and Data Analytics Research Group (AIDA) high-performance computing cluster via SSH. Training is performed on a single NVIDIA A40 GPU (46~GB VRAM). The software stack uses Python with PyTorch as the deep learning framework, scikit-learn for the lightweight recruiter-side models, and the Sentence Transformers library for Qwen3 text embeddings.

\section{User-Side Recommendation Experiments}
\label{sec:exp_user}
% ============================================================
 
\subsection{Experiment Goal}
\label{sec:exp_user_goal}
The goal of the user-side experiments is to train and evaluate a two-tower model that can rank relevant jobs highly for cold-start users — users with no interaction history in the training period. The model is trained on Windows 1--4, validated on Windows 5--6, and evaluated on Window 7, where it must generalise to entirely new users and jobs. Success is measured primarily by \gls{ROC-AUC} during training, as this metric is least sensitive to the candidate pool size of the validation set combined with the practical utility of the model. The practical utility of the model is assessed qualitatively at inference time by inspecting recommendations for a sample of test users against the full Window 7 job pool.
 
\subsection{Subsampling and Negative Sampling Strategy}
\label{sec:negative_sampling}
From the 189,657 users in the training set, a random sample of 25,000 users per window is drawn to create a manageable training set of 100,000 users. With a median of 2 applications per user, this results in approximately 200,000 positive user-job pairs for training. The validation set is not subsampled and contains all 78,428 users having approximately 156,856 positive user-job pairs for validation. 

Because the training data contains only positive interactions (jobs a user applied to), negative examples must be constructed explicitly. A random negative sampling approach — drawing jobs uniformly at random — would produce trivially easy negatives: a software engineer from Texas would be contrasted with nursing jobs in Maine, and the model could separate them on geography or title alone without learning meaningful preference signals.
 
The negative sampling strategy is therefore designed to produce \emph{hard} and \emph{realistic} negatives. For each positive pair $(u, j^+)$, four negatives are sampled according to a \textbf{2:1:1 ratio}:
\begin{itemize}
    \item \textbf{2 cross-state negatives}: jobs from states other than the user's own state, sampled from the same temporal window. These teach the model that geographic fit is a genuine signal.
    \item \textbf{1 same-state negative}: a job from the user's state but a different city, active in the same window. This forces the model to look beyond state-level location and discriminate on career content.
    \item \textbf{1 same-city negative}: a job posted in the user's city but one the user did not apply to. These are the hardest negatives, as they share the user's location and are still unapplied to, pressuring the model to learn semantic fit.
\end{itemize}
 
The 2:1:1 strategy ensures the training distribution is representative of the real inference setting, where the model must rank jobs across the entire country, and resolves this clustering artefact as demonstrated in Section~\ref{sec:exp_user_inference}. 

\subsection{Hyperparameters and Training Settings}
\label{sec:exp_user_hyperparameters}
The model is trained for a maximum of 50 epochs with early stopping (patience~= 5) based on validation loss. The Adam optimiser is used with a learning rate of $1e^{-3}$ and a batch size of 1024. The embedding dimension $d$ is set to 64.
\subsection{Ablation Study}
\label{sec:exp_user_ablation}
 
To determine the optimal model configuration, a systematic ablation study is conducted comparing two design choices: whether to include location features (city and state) and whether to apply L2 normalisation to the output embeddings. All configurations are trained with the 2:1:1 negative sampling strategy described in Section~\ref{sec:negative_sampling}, with early stopping (patience~= 5). Table~\ref{tab:ablation_user} reports the results at the best validation checkpoint for each configuration.
 
A note on interpreting the ranking metrics: Hit@K, Recall@K and NDCG@K are computed against the validation set's balanced candidate pool (positive and sampled negative jobs per user) rather than the full job catalogue. For example if a user has applied to 2 jobs, the metrics are computed against a pool of 2 positive jobs and 8 sampled negative jobs using the negative sampling strategy discussed in Section~\ref{sec:negative_sampling}. As discussed in Section~\ref{sec:prelim_metrics}, this makes their absolute values considerably more optimistic than what would be observed at full-scale inference. AUC-ROC is therefore used as the primary comparison criterion, as it is less sensitive to this pool-size effect. This caveat applies equally to the final model results in Section~\ref{sec:user_results}.

    \label{tab:ablation_user}

Two findings emerge from the results. First, \textbf{L2 normalisation consistently hurts performance} regardless of whether location features are present. Normalising output embeddings to unit norm removes their magnitude, which prevents the model from encoding match confidence in the scale of the dot product. Without normalisation, the magnitude acts as an additional degree of freedom that the model can use to express certainty, benefiting both the loss and the ranking quality. This is a interesting finding considering that cosine similarity is a common practice to calculate embedding similarity \cite{you2025semanticsanglecosinesimilarity}.
 
Second, \textbf{including location features improves performance substantially} — \gls{ROC-AUC} rises from 0.8641 to 0.9242. The 2:1:1 strategy exposes the model to geographically diverse negatives during training. This prevents the model from learning city-density patterns and instead allows it to genuinely learn state-level geographic preference as a meaningful signal. The result is that the location-included model not only scores higher offline but also produces geographically sensible recommendations at inference, as confirmed by the qualitative evaluation in Section~\ref{sec:exp_user_inference}.
 
Based on both quantitative and qualitative evidence, the final model \textbf{includes location features and applies no L2 normalisation}. A complete breakdown of all four configurations across all ranking metrics is provided in Table~\ref{app:tab:full_ablation} in the Appendix.

\section{Recruiter-Side Recommendation Experiments}
\label{sec:exp_recruiter}
% ============================================================
 
\subsection{Experiment Goal}
\label{sec:exp_recruiter_goal}
 
The recruiter-side experiments address three questions. First, does the \gls{LLM}-based labeling pipeline produce a training signal rich enough to train a lightweight ranker — one that correctly separates qualified from unqualified applicants on jobs it has never seen? Second, which classifier best exploits the engineered feature set described in Section~\ref{sec:recruiter_features}? Third, does the choice of negative construction strategy — \gls{LLM}-evaluated hard negatives versus synthetically sampled non-applicants — have a measurable effect on ranking quality? Success is assessed both quantitatively via AUC-ROC as the primary metric, and qualitatively through a sanity check that inspects model scores on real applicant pools.
 
\subsection{Data Generation}
\label{sec:exp_recruiter_datagen}
 
Because no ground-truth recruiter feedback exists in the dataset, training labels must be generated synthetically. The method is described in Section~\ref{sec:recruiter_data_gen}; this section provides the implementation details specific to this experiment.
 
\paragraph{Labeling setup}
Labels are generated using the Qwen3.5 (35B) model served locally via the Ollama API. For computational feasibility, a sample of jobs is drawn from Windows~1--4; for each job, up to 20 applicants are evaluated in a single batched prompt. The \gls{LLM} receives the job description alongside all candidate profiles in the batch and returns a structured JSON response. The final prompt used is:
\begin{tcolorbox}[colback=blue!5!white, colframe=blue!75!black, title=LLM Prompt for Recruiter-Side Labeling]
Task: You are an HR recruiter. You need to check how good a person fits the job based on user profile and job description (IMPORTANT: Treat each job-user pair independently).
            Assign a fit level:  -"Very Good Fit": Meets 100% of Must-Haves AND meets 50% or more of Nice-to-Haves AND has 0 Deal-Breakers.
                                -"Good Fit": Meets 100% of Must-Haves (OR misses exactly 1 Must-Have but compensates with extensive relevant experience) AND has 0 Deal-Breakers.
                                -"Poor Fit": Missing 2 or more Must-Haves OR has exactly 1 Deal-Breaker.
                                -"Very Poor Fit": Missing 3 or more Must-Haves OR has 2 or more Deal-Breakers.
            
            Return a JSON object with a "results" key containing an array of candidate decisions:
            {{"results": [{{"candidate_id": <id>, "must_haves": "xxx", "nice_to_haves": "xxx", "deal_breakers": "xxx", "reasoning": "xxx", "fit_level": "Good Fit"}}]}}

            Extra Notes:
            - Be strict as these jobs have many applicants. Only candidates that truly meet the requirements should be rated as "Very Good Fit" or "Good Fit". If there are any significant gaps in must-haves, it should be reflected in the fit level and reasoning.
            - Be objective and specific in your reasoning. Focus on concrete matches/mismatches between the candidate's profile and the job requirements. Avoid vague statements.
            - Keep the JSON output concise. Fields shouldn't be phrases but just short descriptors, for example must haves "Bachelor's Degree in Computer Science, 5+ years of experience in software development". 
              The reasoning should be very brief (max 3 sentences) but specific to the candidate's profile and the job description.
            - If a feature is empty, missing or NaN in Degree, Major, Experience or History, assume the candidate does not have that feature. For example, if Degree is empty, assume no degree. If History is empty, assume no relevant job history.
            - Assume all applicants are adults (18+), if specific age is missing.
            - Assume availability is not an issue unless explicitly stated.
            - Assume physical ability is not an issue.

            Job Description:
            {job_desc}

            Candidate Profiles:
            {profiles_text}
\end{tcolorbox}

This prompt contains explicit rules, notes and output format to ensure consistency. The prompt starts with a clear task definition and a precise fit level rules. This is followed by detailed instructions on the expected output format, including the required JSON structure and specific content for each field. By providing fields for must-haves, nice-to-haves, deal-breakers and reasoning, the prompt encourages the model to reason and explain its decisions rather than just outputting a label. Then extra notes are established to guide the model towards a more conservative and specific evaluation style. These notes were iteratively defined by inspecting model outputs and adjusting the prompt to address common issues. For example some rows have missing values in key features like Degree or Experience, and without explicit instructions the model would often ignore these and assume the candidate had a degree or relevant experience, leading to overly optimistic fit levels. By instructing the model to treat missing values as an absence of that feature, it produces more realistic assessments. Finaly both job descriptions and candidate profiles are included in the prompt.

\paragraph{Validation set}
A separate held-out small labeled set is generated for the qualitative sanity check targeting a disjoint sample of jobs from Windows~5--6. This set contains only real applicants with their \gls{LLM} labels — no synthetic negatives are added — providing a clean probe of whether the model correctly ranks good fits above poor ones among actual candidates on completely unseen jobs.
 
\subsection{Experiment Setting}
\label{sec:exp_recruiter_setting}
 
\paragraph{Data split.}
To evaluate generalisation to unseen jobs, a group-based split by job identity is used rather than a random instance split. All unique jobs are randomly shuffled and partitioned into 80\% training, 10\% validation, and 10\% test. All candidate-job pairs for a given job are placed in the same partition, ensuring the model is never evaluated on a job seen during training.
 
\paragraph{Negative sampling variants.}
Two negative construction strategies are compared to isolate the effect of negative type:
\begin{itemize}
    \item \textbf{LLM negatives}: Poor and Very Poor Fit applicants as labeled by the \gls{LLM} — hard negatives from the real applicant pool.
    \item \textbf{Synthetic negatives}: non-applicants sampled randomly from the broader user pool, filtered so that their job history shares no keywords with the job title — easy negatives.
\end{itemize}
Both variants use the same positive set and are evaluated against the same held-out test split, with XGBoost as the classifier.
 
\paragraph{Training configuration.}
Stratified 5-fold cross-validation is used for model selection, preserving the class ratio in each fold. All four candidate classifiers (Logistic Regression, Random Forest, XGBoost, soft-voting ensemble) are evaluated under the same protocol. All features are standardised using parameters estimated on the training fold only to prevent data leakage. The final model is retrained on all data and serialised together with the fitted preprocessing artifacts for inference.
