\section{General Experiments Setting}
\label{sec:exp_settings}

\subsection{Dataset}
\label{sec:exp_dataset}
All experiments are conducted on the CareerBuilder Job Recommendation dataset~\cite{careerbuilderdataset}, consisting of real-world job applications, user profiles and job postings from CareerBuilder.com over a 13-week period. The dataset is organised into seven consecutive 13-day temporal windows where users apply to jobs which are active in the same window. Table~\ref{tab:dataset_stats} summarises the scale of the full dataset.

The two-tower architecture instead uses interactions as a training signal while generalising through user and job profile features, making it robust to sparse data.

Rather than using the original within-window train/test labels provided by the dataset, a temporal split across windows is applied (Figure~\ref{fig:custom_temporal_split}). Windows 1--4 form the training set and Windows 5--7 form the validation and test set, with Windows 5--6 used for validation and Window 7 reserved for final evaluation.

Users marked \texttt{Split=Test} are excluded entirely (22,838 users). These users made five or more applications during the withheld 4-day test period of the original competition. Of these, 43\% have no recorded interactions in the training period whatsoever, as their only observable activity falls within the withheld test period. Including them would introduce users with structurally missing interaction records into the evaluation set, so they are excluded entirely.

This design has three consequences. First, there is a strict temporal boundary: the model never sees any interaction from the evaluation period during training. Second, the evaluation is a genuine cold-start scenario — no user appears in both the training and evaluation sets. Third, using all active users from each window group (rather than filtering by activity thresholds) avoids biasing the evaluation towards highly-engaged users. Table~\ref{tab:split_stats} shows the resulting split sizes.

\subsection{Hardware and Software Configuration}
\label{sec:hardware}

All experiments are run on the Artificial Intelligence and Data Analytics Research Group (AIDA) high-performance computing cluster via SSH. Training is performed on a single NVIDIA A40 GPU (46~GB VRAM). The software stack uses Python with PyTorch as the deep learning framework, scikit-learn for the lightweight recruiter-side models, and the Sentence Transformers library for Qwen3 text embeddings.

\section{User-Side Recommendation Experiments}
\label{sec:exp_user}
% ============================================================
 
\subsection{Experiment Goal}
\label{sec:exp_user_goal}
The goal of the user-side experiments is to train and evaluate a two-tower model that can rank relevant jobs highly for cold-start users — users with no interaction history in the training period. The model is trained on Windows 1--4, validated on Windows 5--6, and evaluated on Window 7 by doing sanity checks, where it must generalise to entirely new users and jobs. Success is measured primarily by \gls{ROC-AUC} during training, as this metric is least sensitive to the candidate pool size of the validation set combined with the practical utility of the model. The practical utility of the model is assessed qualitatively at inference time by inspecting recommendations for a sample of test users against the full Window 7 job pool.
 
\subsection{Subsampling and Negative Sampling Strategy}
\label{sec:negative_sampling}
From the 189,657 users in the training set, a random sample of 25,000 users per window is drawn to create a manageable training set of 100,000 users. With a median of 2 applications per user, this results in approximately 200,000 positive user-job pairs for training. The validation set is not subsampled and contains all 78,428 users having approximately 156,856 positive user-job pairs for validation. 

Because the training data contains only positive interactions (jobs a user applied to), negative examples must be constructed explicitly. A random negative sampling approach — drawing jobs uniformly at random — would produce trivially easy negatives: a software engineer from Texas would be contrasted with nursing jobs in Maine, and the model could separate them on geography or title alone without learning meaningful preference signals.
 
The negative sampling strategy is therefore designed to produce \emph{hard} and \emph{realistic} negatives. For each positive pair $(u, j^+)$, four negatives are sampled according to a \textbf{2:1:1 ratio}:
\begin{itemize}
    \item \textbf{2 cross-state negatives}: jobs from states other than the user's own state, sampled from the same temporal window. These teach the model that geographic fit is a genuine signal.
    \item \textbf{1 same-state negative}: a job from the user's state but a different city, active in the same window. This forces the model to look beyond state-level location and discriminate on career content.
    \item \textbf{1 same-city negative}: a job posted in the user's city but one the user did not apply to. These are the hardest negatives, as they share the user's location and are still unapplied to, pressuring the model to learn semantic fit.
\end{itemize}
 
The 2:1:1 strategy ensures the training distribution is representative of the real inference setting, where the model must rank jobs across the entire country, and resolves this clustering artefact as demonstrated in Section~\ref{sec:exp_user_inference}. 

\subsection{Hyperparameters and Training Settings}
\label{sec:exp_user_hyperparameters}
The model is trained for a maximum of 50 epochs with early stopping (patience~= 5) based on validation loss. The Adam optimiser is used with a learning rate of $10^{-3}$ and a batch size of 1024. The embedding dimension $d$ is set to 64.
\subsection{Ablation Study}
\label{sec:exp_user_ablation}
 
To determine the optimal model configuration, a systematic ablation study is conducted comparing two design choices: whether to include location features (city and state) and whether to apply L2 normalisation to the output embeddings. All configurations are trained with the 2:1:1 negative sampling strategy described in Section~\ref{sec:negative_sampling}, with early stopping (patience~= 5). Table~\ref{tab:ablation_user} reports the results at the best validation checkpoint for each configuration.
 
A note on interpreting the ranking metrics: Hit@K, Recall@K and NDCG@K are computed against the validation set's balanced candidate pool (positive and sampled negative jobs per user) rather than the full job catalogue. For example if a user has applied to 2 jobs, the metrics are computed against a pool of 2 positive jobs and 8 sampled negative jobs using the negative sampling strategy discussed in Section~\ref{sec:negative_sampling}. As discussed in Section~\ref{sec:prelim_metrics}, this makes their absolute values considerably more optimistic than what would be observed at full-scale inference. AUC-ROC is therefore used as the primary comparison criterion, as it is less sensitive to this pool-size effect. This caveat applies equally to the final model results in Section~\ref{sec:user_results}.

    \label{tab:ablation_user}

Two findings emerge from the results. First, \textbf{L2 normalisation consistently hurts performance} regardless of whether location features are present. Normalising output embeddings to unit norm removes their magnitude, which prevents the model from encoding match confidence in the scale of the dot product. Without normalisation, the magnitude acts as an additional degree of freedom that the model can use to express certainty, benefiting both the loss and the ranking quality. This is an interesting finding considering that cosine similarity is a common practice to calculate embedding similarity \cite{you2025semanticsanglecosinesimilarity}.
 
Second, \textbf{including location features improves performance substantially} — \gls{ROC-AUC} rises from 0.8641 to 0.9242. The 2:1:1 strategy exposes the model to geographically diverse negatives during training. This prevents the model from learning city-density patterns and instead allows it to genuinely learn state-level geographic preference as a meaningful signal. The result is that the location-included model not only scores higher offline but also produces geographically sensible recommendations at inference, as confirmed by the qualitative evaluation in Section~\ref{sec:exp_user_inference}.
 
Based on both quantitative and qualitative evidence, the final model \textbf{includes location features and applies no L2 normalisation}. A complete breakdown of all four configurations across all ranking metrics is provided in Table~\ref{app:tab:full_ablation} in the Appendix.

\subsection{Limitations}
\label{sec:exp_user_limitations}
Despite strong quantitative performance and qualitatively sensible recommendations for users with stable career histories, 3 structural limitations of the current 
design are worth noting.

\paragraph{Overfitting to the training distribution.}
Figure~\ref{fig:trainval} reveals a growing divergence between training and validation loss after approximately epoch~5. While validation loss plateaus 
around $0.27$, training loss continues to decrease to $0.20$, suggesting the model begins to overfit to the training windows. This is consistent with the 
cold-start evaluation setup: the model is trained on Windows~1--4 and evaluated on entirely new users and jobs from Windows~5--7, meaning the distribution shift 
between train and evaluation is structural rather than random. Dropout and batch normalisation partially mitigate this, but the gap suggests the model has 
memorised aspects of the training user-job distribution that do not fully generalise. Possible mitigations include stronger regularisation, increased dropout rates, or data augmentation techniques such as feature masking during 
training.
\paragraph{Temporally flat job history representation.}
The job history embedding is produced by encoding the three most recent job titles 
as a single concatenated string and passing it through the Qwen encoder. This means 
all three titles contribute equally to the resulting vector, regardless of how recent 
they are and the duration of their employment. Recent jobs contain more signal about the user's current preferences and are more predictive of their next move, while older jobs may reflect past interests or even noise. The duration of each job is also relevant — a user with a 10-year tenure as a software engineer followed by a 3-month stint in retail likely has different preferences than a user with the opposite pattern. However, the CareerBuilder dataset does not provide employment duration in the user history, making this signal inaccessible to the current model.

A natural extension would be to embed each title independently and compute a weighted 
sum with recency weights, for example:
\begin{equation}
    \mathbf{e}_{\text{history}} = 0.5 \cdot \mathbf{e}_{t_1} 
                                + 0.3 \cdot \mathbf{e}_{t_2} 
                                + 0.2 \cdot \mathbf{e}_{t_3}
\end{equation}
where $\mathbf{e}_{t_1}$ is the embedding of the most recent title. This would 
encode both the content and the direction of career movement into the user 
representation. This limitation was not apparent in the two cases presented in 
Section~\ref{sec:exp_user_inference}, as both users had coherent and stable 
career histories. It is expected to surface most clearly in evaluation on users 
with mixed or transitioning profiles.

\paragraph{City and State embedding sparsity.}
City and state are encoded as categorical features with learned embeddings. Cities and states that appear rarely in Windows~1--4 have fewer training examples and therefore an undertrained embedding. For users located in such cities, the geographic signal 
is weak and the model compensates by relying more heavily on the job history 
representation — which then exposes the limitation above. This effect is expected 
to be most pronounced for users outside major metropolitan areas.

\section{Recruiter-Side Recommendation Experiments}
\label{sec:exp_recruiter}
% ============================================================
 
\subsection{Experiment Goal}
\label{sec:exp_recruiter_goal}
 
The recruiter-side experiments address two design choices that must be made before a final model can be deployed. The first is \textbf{classifier selection}: given the engineered feature set described in Section~\ref{sec:recruiter_features}, which model family best exploits it? The second is \textbf{negative strategy selection}: given the chosen classifier, does the choice of negative construction — \gls{LLM}-evaluated hard negatives from the applicant pool, synthetically sampled non-applicants or a combination of both — have a measurable effect on ranking quality, and which strategy yields the more useful model? These two questions are answered sequentially in Sections~\ref{sec:exp_recruiter_model_comparison} and~\ref{sec:exp_recruiter_negatives}. Success is assessed both quantitatively via the metrics introduced in Section~\ref{sec:prelim_classification}, and qualitatively through sanity checks.
 
\subsection{Data Generation}
\label{sec:exp_recruiter_datagen}
 
Because no ground-truth recruiter feedback exists in the dataset, training labels must be generated synthetically. The method is described in Section~\ref{sec:recruiter_data_gen}; this section provides the implementation details specific to this experiment.
 
\paragraph{Labeling setup}
Labels are generated using the Qwen3.5 (35B) model served locally via the Ollama API. For computational feasibility, a sample of jobs is drawn from Windows~1--4; for each job, up to 20 applicants are evaluated in a single batched prompt. The \gls{LLM} receives the job description alongside all candidate profiles in the batch and returns a structured JSON response. The final prompt used is:

{\small
\begin{verbatim}
Task: You are an HR recruiter. Evaluate how well each person fits the job
based on their profile and the job description.
(IMPORTANT: Treat each job-user pair independently.)

Assign a fit level:
- "Very Good Fit": Meets 100% of Must-Haves AND 50%+ of Nice-to-Haves
  AND 0 Deal-Breakers.
- "Good Fit": Meets 100% of Must-Haves (OR misses 1 Must-Have but
  compensates with extensive relevant experience) AND 0 Deal-Breakers.
- "Poor Fit": Missing 2+ Must-Haves OR has exactly 1 Deal-Breaker.
- "Very Poor Fit": Missing 3+ Must-Haves OR has 2+ Deal-Breakers.

Return a JSON object:
{"results": [{"candidate_id": <id>, "must_haves": "...",
  "nice_to_haves": "...", "deal_breakers": "...",
  "reasoning": "...", "fit_level": "Good Fit"}]}

Notes:
- Be strict. Only candidates that truly meet requirements get Good Fit.
- Be objective. Focus on concrete matches/mismatches.
- If Degree, Major, Experience or History is empty/NaN, assume the
  candidate does not have that feature.
- Assume all applicants are 18+, available, and physically able.

Job Description: {job_desc}
Candidate Profiles: {profiles_text}
\end{verbatim}
}

This prompt contains explicit rules, notes and output format to ensure consistency. The prompt starts with a clear task definition and a precise fit level rules. This is followed by detailed instructions on the expected output format, including the required JSON structure and specific content for each field. By providing fields for must-haves, nice-to-haves, deal-breakers and reasoning, the prompt encourages the model to reason and explain its decisions rather than just outputting a label. Then extra notes are established to guide the model towards a more conservative and specific evaluation style. These notes were iteratively defined by inspecting model outputs and adjusting the prompt to address common issues. For example some rows have missing values in key features like Degree or Experience, and without explicit instructions the model would often ignore these and assume the candidate had a degree or relevant experience, leading to overly optimistic fit levels. By instructing the model to treat missing values as an absence of that feature, it produces more realistic assessments. Finaly both job descriptions and candidate profiles are included in the prompt. 

An example output for a single candidate is shown below:
 
\begin{listing}[H]
\begin{minted}{json}
{
  "results": [
    {
      "candidate_id": 349089,
      "must_haves": "Associates degree, 6mo experience/leadership,
                     valid license, work authorisation",
      "nice_to_haves": "Bachelors degree, sales/CS background",
      "deal_breakers": "None identified",
      "reasoning": "Candidate profile shows degree and experience as
                    empty. Job requires Associates degree and 6 months
                    experience. Missing these core requirements.",
      "fit_level": "Poor Fit"
    }
  ]
}
\end{minted}
\caption{Example LLM JSON output for a single candidate-job evaluation.}
\label{lst:llm_json_output}
\end{listing}
 
The structured output format enforces consistency: every response contains an explicit must-haves assessment, a reasoning trace, and a fit level drawn from a fixed four-value vocabulary. Responses that fail JSON parsing or contain unexpected fit level values are discarded.
 
\paragraph{Label distribution.}
The resulting dataset contains \textbf{5,896} labeled pairs across \textbf{1511} unique jobs. Table~\ref{tab:recruiter_label_dist} shows the fit level distribution. The negative class (Poor and Very Poor Fit) accounts for 54.1\% of pairs, slightly outnumbering positives. This reflects the conservative evaluation style enforced by the prompt: missing values in profile fields are treated as absent features, and the model is instructed to be strict (see Sect~\ref{sec:exp_recruiter_prompt}). Class weights are still applied during training to ensure each class contributes proportionally to the loss, with weights set inversely proportional to class frequency.

\paragraph{Validation set}
A separate held-out small labeled set is generated for the qualitative sanity check targeting a disjoint sample of jobs from Windows~5--6. This set contains only real applicants with their \gls{LLM} labels — no synthetic negatives are added — providing a clean probe of whether the model correctly ranks good fits above poor ones among actual candidates on completely unseen jobs.
 
\subsection{Experiment Setting}
\label{sec:exp_recruiter_setting}
 
\paragraph{Data split}
To evaluate generalisation to unseen jobs, a group-based split by job identity is used rather than a random instance split. All unique jobs are randomly shuffled and partitioned into 80\% for cross-validation and final model training, and 20\% held-out test; all candidate-job pairs for a given job land in the same partition. The test set is used only once, after the final model has been chosen.
 
\paragraph{Negative sampling variants}
Three negative construction strategies are compared to isolate the effect of negative type:
\begin{itemize}
    \item \textbf{LLM negatives}: Poor and Very Poor Fit applicants as labeled by the \gls{LLM} — hard negatives from the real applicant pool.
    \item \textbf{Synthetic negatives}: non-applicants sampled randomly from the broader user pool, filtered so that their job history shares no keywords with the job title — easy negatives.
    \item \textbf{Combined negatives}: an equal 50/50 mix of LLM and synthetic negatives (1,352 of each), exposing the model to both hard and easy discrimination during training.
\end{itemize}
All variants use the same positive set. Each variant is evaluated on a held-out test set of the same 20\% of jobs, but the test pairs differ by strategy: for the LLM-negative model the test negatives are Poor/Very Poor Fit applicants; for the synthetic model they are random non-applicants; for combined, a mix of both. This means each model is tested in its own operating regime rather than against a single shared test set. Table~\ref{tab:recruiter_dataset_sizes} summarises the resulting dataset sizes.

\paragraph{Training configuration}
Group 5-fold cross-validation is used for model selection, ensuring jobs are not split across folds. All four candidate classifiers (Logistic Regression, Random Forest, XGBoost, soft-voting ensemble) are evaluated under the same protocol. All features are standardised using a \texttt{StandardScaler} fitted on each training fold only, to prevent data leakage into the validation fold. \gls{TF-IDF} is likewise fitted on the training fold's job texts within each fold and then used to transform both the training and validation fold. \gls{PCA} is also refitted per fold on the training partition of the interaction matrix. The final model is retrained on the full 80\% pool with \gls{TF-IDF}, \gls{PCA}, and the scaler all fitted on that same 80\%, and all artifacts are serialised for inference.
 
\paragraph{Evaluation metrics}
Performance is reported using Accuracy, Precision, Recall, F1-score, and AUC-ROC as defined in Section~\ref{sec:prelim_metrics}. AUC-ROC is the primary model selection criterion. In the second stage of the experiment (negative strategy comparison), the same metrics are used to compare the final XGBoost model trained on each negative strategy, combined with a qualitative sanity check on different test sets to assess real-world ranking quality.
 
\subsection{Stage 1: Classifier Selection}
\label{sec:exp_recruiter_model_comparison}
 
All four candidate classifiers are compared on the \gls{LLM}-negative dataset, holding the training data fixed so that the only variable is the model type. The choice of this dataset is motivated by the fact that this is a harder classification task compared to the synthetic negative dataset. Table~\ref{tab:recruiter_results_cv} reports 5-fold cross-validation results; Table~\ref{tab:recruiter_results_test} reports the held-out test set performance of the selected model.

The Ensemble achieves the highest cross-validation AUC (0.696), but the gap over XGBoost (0.690) is 0.006 — well within the standard deviation of both models (0.017 and 0.019 respectively). This difference is not statistically meaningful. Random Forest is similarly tied on AUC (0.691) but has markedly lower Recall (0.528 vs.\ 0.588 for XGBoost), meaning it misses a larger fraction of genuinely qualified candidates. In a recruitment context, missing good candidates is the more costly error. XGBoost is therefore selected as the final classifier: it matches the Ensemble on AUC within noise, outperforms Random Forest on Recall, and provides native feature importance scores that support the interpretability of the model.

\subsubsection{Feature Importance}
\label{sec:exp_recruiter_feature_importance}

\paragraph{Interaction matrix PCA}
The embedding interaction matrix $\mathbf{m}_{uj} \in \mathbb{R}^{2d_{\text{text}}}$ has 200 dimensions. \gls{PCA} is applied to reduce the interaction matrix to $d_{\text{pca}} = 80$ components, retaining 92.9\% of the total variance. This compression is justified on two grounds. First, the Hadamard product and absolute difference of the same pair of embeddings share significant covariance structure, meaning a large fraction of the 200 dimensions are redundant — a finding confirmed by the high variance retention at only 40\% of the original dimensionality. Second, reducing the feature space lowers the risk of XGBoost fitting to noise in the interaction dimensions, even with 5,896 training pairs.

\paragraph{Feature importance analysis}
Table~\ref{tab:recruiter_feature_importance} shows the normalised feature 
importance for each of the three base classifiers on the last cross-validation 
fold. The \gls{PCA} interaction components dominate across all models — 
accounting for 69.2\%, 83.2\%, and 85.6\% of total importance in Logistic 
Regression, Random Forest, and XGBoost respectively. This confirms that the 
element-wise interaction between user and job Qwen embeddings captures the 
majority of the discriminative signal, validating the design choice of computing 
the full interaction matrix rather than relying solely on scalar cosine similarity.

Among the scalar features, the pattern differs by model family. In Logistic Regression, the Qwen cosine similarity (12.6\%) is the second most important feature, suggesting the linear model benefits from the direct scalar similarity signal. In Random Forest and XGBoost, \texttt{tfidf\_overlap} ranks higher than cosine similarity, suggesting that tree-based models extract more value from explicit keyword matching once the dominant PCA signal is accounted for. \texttt{TotalYearsExperience} ranks consistently across all three models. Both \texttt{degree\_match} and \texttt{full\_profile\_cosine\_sim} contribute negligibly across all classifiers --- under 2.6\% in the best case, and zero in XGBoost --- indicating they are subsumed by the PCA interaction and TF-IDF features. Despite their low importance, both features are retained in the final model. XGBoost's built-in regularisation already suppresses low-importance features during training, so removing them would not meaningfully change performance. Retaining them also preserves consistency with the feature engineering pipeline described in Section~\ref{sec:recruiter_features} and avoids the need for a separate retraining run to confirm that the delta is negligible.

\subsection{Stage 2: Negative Strategy Selection}
\label{sec:exp_recruiter_negatives}
 
Having established XGBoost as the strongest classifier, the model type is now held fixed and the negative construction strategy is varied. Table~\ref{tab:recruiter_neg_comparison} reports XGBoost test set performance for each strategy, where each model is evaluated on a test set constructed with the same negative type as its training data.

A critical caveat applies before interpreting these numbers: the three test sets are not equivalent in difficulty. The synthetic model is tested on random non-applicants — an easy discrimination task — while the LLM model is tested on poor-fit applicants from the real pool — a hard one. The AUC scores therefore reflect both model quality \emph{and} task difficulty, and cannot be compared directly on an absolute basis.

With that in mind, the synthetic model achieves the highest AUC (0.852) because it solves the simplest version of the problem: almost any sensible feature should separate a strong applicant from a random non-applicant. The LLM model achieves the lowest AUC (0.724), correctly reflecting the genuine difficulty of separating good applicants from poor-fit ones within the same self-selected pool. The combined model sits between the two (0.755), having seen both types of negatives during training and being tested on both.

Despite its lower raw metrics, the \textbf{LLM-negative model is chosen for deployment}. The deployment scenario mirrors the LLM test set: a recruiter using the system sees real applicants — not random people — and needs to distinguish genuinely qualified candidates from those who applied despite a poor fit. The sanity check in Section~\ref{sec:exp_recruiter_sanity} provides an additional test: if the LLM model assigns higher scores to applicants than to random non-applicants on held-out jobs (a test it was never trained for), it confirms the model has learned genuine fit signals rather than artefacts of the training negatives.

A secondary finding concerns feature importance. Across all three models (Table~\ref{tab:recruiter_feature_importance}), the PCA interaction components dominate — but their share drops noticeably when training on synthetic negatives (XGB: 81.4\% vs 85.6\% for LLM). TF-IDF overlap compensates, rising to 9.3\% from 5.2\%. This pattern suggests that on easy negatives the model can rely more on surface keyword matching to separate careers, whereas the harder LLM negatives force the model to use the deeper embedding interactions.

\subsubsection{Final Model}
\label{sec:exp_recruiter_final}

The two-stage selection process yields a clear conclusion: \textbf{XGBoost trained on LLM negatives} is the final recruiter-side model. Despite its lower raw metrics relative to the synthetic variant, it operates in the most realistic setting — distinguishing genuinely qualified applicants from poor-fit ones within the same self-selected pool — which directly mirrors deployment. This model is serialised and used as the recruiter-side suitability scorer in Chapter~\ref{chap:congestion_balancing}.
